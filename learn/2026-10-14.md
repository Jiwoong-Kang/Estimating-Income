### 1. 전처리 모듈(`src/preprocess.py`)을 만드는 이유

- EDA에서 내린 전처리 결정을 코드 한 곳에 모아두고, 모든 모델 노트북이 이 파일의 함수만 쓰게 한다. → **모든 모델이 똑같은 손질을 거치므로 공평하게 비교할 수 있다.**
- 한 번에 다 만들지 않고 조각마다 `test.py`로 실행해서 확인한 뒤 다음 조각으로 넘어갔다.

### 2. 손질 단계 정리

| 단계 | 하는 일 | 사용한 도구 |
|---|---|---|
| 1 | 입력(X)과 정답(y) 나누기, 필요 없는 열(fnlwgt, education) 제거 | `split_features_target` |
| 2 | 글자 항목의 빈칸을 "Missing"으로 채우기 | `SimpleImputer` |
| 3 | 글자를 0/1 열로 펼치기 (원-핫 인코딩) | `OneHotEncoder` |
| 4 | 숫자 항목 다듬기 (로그 변환, 크기 맞추기) | `FunctionTransformer(np.log1p)`, `StandardScaler` |
| 묶기 | 열 묶음마다 알맞은 도구 배정 | `ColumnTransformer` |
| 조립 | 전처리 + 모델을 한 줄로 연결 | `Pipeline` |

- fnlwgt는 표본 가중치(이 사람이 인구 몇 명을 대표하는가)라서 개인의 소득과 관계없다. education은 education-num과 1:1로 같은 정보라서 숫자 쪽만 남긴다.

### 3. 원-핫 인코딩: 글자를 숫자로 바꾸는 방법

- 컴퓨터는 글자를 계산할 수 없으므로, **항목 안의 값마다 "이 값이야?"라는 열을 하나씩 만들고** 해당하면 1, 아니면 0을 넣는다.
- 1, 2, 3 같은 번호를 붙이지 않는 이유: 모델이 "3이 1보다 크다"는 없는 순서를 배워버린다.
- 한 사람은 원래 항목 하나마다 1이 딱 한 번 나온다. (예: 인종 열 5개 중 1은 하나)
- 글자 항목 7개 → **66열**. 50번 미만으로 나오는 드문 값은 `min_frequency=50`으로 "기타(infrequent)" 열 하나에 모았다. (native-country 42개 값 → 23열)
- 열 이름은 `원래항목_값` 형태다. (예: `workclass_Missing`) `workclass_Missing`이 보이면 빈칸 채우기가 제대로 된 것이다.

### 4. 숫자 항목 다듬기

- **크기 맞추기(StandardScaler):** 각 값을 "평균에서 얼마나 떨어져 있나"로 바꾼다. 평균은 0, 보통 차이는 1이 된다. 범위가 제각각인 항목(나이 17~90, capital-gain 0~99999)을 공평하게 만든다. k-NN, SVM처럼 숫자 크기로 계산하는 모델에 필요하다.
- **로그 변환(log1p):** 큰 숫자는 많이, 작은 숫자는 조금 줄인다. 자릿수를 세는 것과 비슷하다. 0의 로그는 계산할 수 없어서 1을 더한 뒤 로그를 취하는 `log1p`를 쓴다(0 → 0).
- 순서: 자본 숫자는 **로그 변환 → 크기 맞추기**. 튀는 값을 먼저 눌러야 크기 맞추기가 제대로 된다.
- 로그 변환과 크기 맞추기는 칸 안의 값만 바꾸고 **열 개수는 그대로**다. (2열 넣으면 2열이 나온다, `one-to-one`) 원-핫은 열을 늘린다.

### 5. 스위치(옵션)를 두는 이유

- `scale`(크기 맞추기 할까?), `log_capital`(로그 변환 할까?)은 True/False 스위치다. 기본값은 True.
- 결정 트리처럼 "나이 > 40인가?"로만 나누는 모델은 크기 맞추기나 로그 변환을 해도 결과가 같다. → 같은 함수 하나로 모델마다 다른 손질을 할 수 있다.
- 켜고 끈 결과를 비교하면 리포트의 "무엇이 효과가 있었나"에 쓸 수 있다.
- `"passthrough"`: 아무것도 하지 말고 그대로 통과시키라는 뜻.
- `**preprocess_options`: `이름=값` 형태로 들어온 것을 모아서 받는다. `make_model_pipeline(모델, scale=False)`라고 하면 `scale=False`가 그대로 `build_preprocessor`로 전달된다.

### 6. Pipeline과 ColumnTransformer

- **Pipeline:** (이름표, 도구) 묶음을 순서대로 실행한다. 리스트에 넣은 순서가 곧 실행 순서다.
- **ColumnTransformer:** (이름표, 도구, 적용할 열) 세 칸 묶음. 열 묶음마다 다른 도구를 적용한 뒤 결과를 옆으로 이어 붙인다. 숫자 3열 + 자본 2열 + 원-핫 66열 = **71열**.
- **이름표는 우리가 마음대로 정하는 이름일 뿐**이고, 실제 일은 뒤의 도구가 한다. 이름표가 열 이름 앞에 `이름표__` 형태로 붙어서(예: `numeric__age`, `capital__capital-gain`) 어느 손질을 거쳤는지 알 수 있다.

### 7. fit과 transform, 그리고 데이터 누수

- `fit_transform`은 우리가 만든 함수가 아니라 scikit-learn 도구가 기본으로 가진 기능이다.

| 기능 | 하는 일 |
|---|---|
| `fit` | 데이터를 보고 배운다 (평균, 어떤 값들이 있는지 등) |
| `transform` | 배운 기준대로 바꾼다 |
| `fit_transform` | 둘을 한 번에 |

- **시험 데이터에는 절대 `fit`하지 않는다.** 훈련 데이터로 배운 기준으로 `transform`만 한다. 시험 데이터로 다시 배우면 시험 문제를 미리 엿보는 셈이다. 이것을 **데이터 누수(data leakage)**라고 한다.
- `make_model_pipeline`으로 전처리와 모델을 묶으면 `pipe.fit(X_train, y_train)`과 `pipe.predict(X_test)` 두 줄로 끝나고, 시험 데이터에 실수로 `fit`할 일이 구조적으로 사라진다.

### 8. 첫 번째 전체 실행 결과

- 전처리 + 로지스틱 회귀(LogisticRegression, `max_iter=1000`)로 시험 데이터 정확도 **84.7%**. Dummy 기준선(76.4%)보다 약 8%포인트 높다. → 전처리 전체가 제대로 동작한다.
- `max_iter`: 답을 찾을 때 최대 몇 번까지 고쳐볼지. 기본값 100으로는 부족해서 경고가 뜰 수 있다.
- 불균형 데이터라 정확도만으로는 부족하다. → 다음 단계 `src/evaluate.py`에서 ROC-AUC, F1, 혼동 행렬 등을 함께 본다.

### 9. 실수에서 배운 점

- **다른 파일의 변수는 import해야 쓸 수 있다.** `test.py`에서 `CATEGORICAL_COLS`를 import하지 않아 "Undefined name" 오류가 났다. 파이썬은 파일마다 이름을 따로 관리한다.
- `"Function ... is not accessed"`는 오류가 아니라 편집기(Pylance)의 안내다. 밑줄로 시작하는 함수를 그 파일 안에서 아직 안 썼다는 뜻이고, 나중에 다른 함수에서 부르면 사라진다.
- 값 하나만 틀려도 오류 없이 결과가 틀어질 수 있다. `">50k"`(소문자)로 적어서 y가 전부 0이 되었다. → **실행 결과를 눈으로 확인하는 습관**이 필요하다.
